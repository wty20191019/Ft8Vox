### 1.2 字号 / 间距 / 触摸

- 呼号 **16sp 粗体**，消息 **13sp**，辅助信息 **11sp**。
- 触摸目标 **≥ 48dp**。
- 字体档位「小 / 中 / 大」通过覆盖 `LocalDensity.fontScale`（0.9 / 1.0 / 1.15）统一缩放 sp，**不影响 dp**。
- 顶栏三行紧凑行高：时钟 20sp、辅助行 13sp，合计约 46dp < 56dp。

### 1.3 外壳

- **顶栏固定 56dp**（`heightIn(min = 56.dp)`，第 3 行出现/消失时高度不跳动）。
- **底部状态条常驻**（不属于任何页面，始终存在）：`● RX / 🔴 TX` 脉动、输入电平 `电平 -42 dB`（未接收时 `电平 --`）、解码 `45/min`、总数 `1234`、`QSO 7`、队列 `2`、时间偏差红字「时间不同步」。
- **底部导航 4 项**：操作 / 地图 / 日志 / 设置，当前页高亮蓝色。

## 2. 页面与组件

### 2.1 顶栏 AppBar（56dp）

左：菜单图标（打开频段 / 模式 / 自动程序 / 设置）。

- 菜单里「模式」一行列出 **FT8 / FT4**（当前项带 `●`）。**协议不能热切换**（时隙长度与调制方式在 native 引擎创建时固定），运行中切换会**自动重建引擎**（内部 `stop()` + `start()`，接收短暂中断；发送总开关状态保留、当前 QSO 结束）；未接收时下次开始接收生效。

中：

- 第 1 行（大）：`14:32:17 UTC`
- 第 2 行（小）：`14.074.000 MHz · FT8 · TX：n · 解码 118ms` —— 只显示**我方发射时隙号**（**0/1**，不用奇/偶），取当前锁定的发射周期 `txParity`；**不再显示接收时隙号**。处于我方发射时隙时该段用强调蓝（发射中为红），接收时隙保持弱化色。`解码 nms` 是**最近一次解码耗时**（native `ftx_session_decode`，纯显示），调设置页「解码深度」（最低得分 / LDPC 迭代 / 候选上限 / 单时隙上限）时用它看计算量代价；未接收或还没解码过时整段不显示。
- 第 3 行（小，**仅我方发射时隙、且有报文或正在发射时出现**）：`待发 CQ DX0ABC`（强调蓝）或 `发射中 CQ DX0ABC`（红，回退显示刚发出的 `lastTxText`）。没有报文时该行不显示。
- 未开始接收时第 2/3 行的时隙段与「解码 nms」整段不显示（**关闭发送总开关时仍显示 `TX：n`** —— 只表示发射周期，与是否允许发射无关）；过长时省略号截断。

右：

- 圆点：绿 = RX，红 = TX 脉动。
- 小喇叭图标：点开音频 / VOX 速览（输入电平、前导、看门狗、设备与增益、输出音量）。

#### 2.3.1 瀑布图区

- 全宽；高度档位按**屏高百分比**：**15% / 24%（默认）/ 45%**（最小 150dp，很矮的屏幕上 15% 会被抬到 150dp），见设置页「外观」；默认 24% ＝ 原来「紧凑」档的外观。
- 横轴 0–3000 Hz（`fMin–fMax`），纵轴时间向下滚。
- 归一化自动配色：0–0.25 深蓝、0.25–0.5 青、0.5–0.75 绿→黄、0.75–1.0 橙→红。
- 右下 `TX xxxx Hz`（**下边频**读数）；贴底 3dp 时隙进度条。（右上原 `Ref -50~-10dB` 参考电平文字已删：瀑布配色按噪声底自适应，从不使用固定参考电平，该文字只是沿用的静态标签。）
- 发射频率画成 **红线 + 半透明红条**：**红线＝报文下边频**（就是报文音频频率本身，右下角读数取它）；
  **半透明红条＝整条报文实际占用的带宽** `[f, f + 占用带宽]`（FT8 8 音 × 6.25 Hz = 50 Hz、FT4 ≈ 83 Hz，
  取 `status.protocol.occupiedHz`），用来一眼看出这条报文会占掉频谱的哪一段；红条贴到边界外时自动夹到视口内。
- 交互：**单击 / 水平拖动** → 设发射频点（红线 = 下边频）；**长按** → 先把红线移到按下处、再打开最近一条解码的详情；**双指捏合缩放已去掉**（频率轴固定铺满 `fMin–fMax`，不做缩放/平移）。
- 原「增益 / 噪抑 / 带宽 / 暂停」占位浮条**已删除**；进入操作页且已授权时**自动开始接收**，未授权时空态提示「未开始接收：点此授权并开始接收」。

#### 2.3.2 筛选 Chip 行

一行，最左与最右为固定图标按钮（不随 Chip 横滚）：

- 最左 **🗑「清除解码信息」**：一键清空本会话的解码列表；列表为空时置灰。只清**显示**列表 —— 不写日志、不改「已解码时隙」计数、不影响自动程序。
- 中间：Material **Chip**（可多选）+ 行尾 **🔍「呼号过滤」**（点击展开搜索框，保留呼号/前缀过滤）。
- 最右 **⭐「跟踪 CQ 列表」**（角标 = 跟踪数量，与最左 🗑 对称）。

Chip：全部 / 与我有关 / CQ / 回复 / 73 / 已通联，每项右侧小角标计数（如 `CQ 23`）；选中蓝底白字，未选深灰底浅字。

#### 2.3.3 解码消息列表

- **排序与自动翻页**：列表**新→旧**（最新一条在最上面，最多保留 200 条）；每批新解码到达时**自动翻到最新**；用户手动拖动翻看历史时暂停跟随（不清屏、不打断阅读），把列表滑回顶部后自动恢复跟随。
- 每张卡片（RecyclerView Item）：左侧色条 + 呼号（16sp 粗）/ 网格 / 报告 / 时间；含我呼号时**红字**。
- 空状态：
  - 没解码：「等待解码…」
  - 筛选项为空：「没有符合条件的解码消息」
  - 被过滤 / 未开始接收另有对应文案。

#### 2.3.4 发射抽屉

**收起态（默认）**，一条 **56dp** 条：

- 左：目标 `→ JA1ABC`
- 中：**下次发送 `<报文>`**（**始终显示「下一次会发什么」**：发射途中改目标 / QSO 推进这里会跟着变；无计划时「空闲（无下次发送）」）。顶栏第 3 行与之互补：顶栏按「发射中冻结为在播的那条」显示（`displayTxText`）
- 右：**「发送总开关」Switch**（**纯权限**：关 = 只接收，开 = 允许发射，**开关本身不发任何报文**）。大按钮「发送」在展开面板内。

**展开方式**：按住条身向上拖动 = **跟手展开**（条身随手指上移、面板从条身**下方**露出）；松手后按「拉过一半 / 甩动速度 ≥ 800 px/s」吸附到展开或收起（弹性动画，初速与目标同向时才带入）。**点击条身空白处 / 长按条身**同样展开。条身右侧「发送总开关」只吃自己的点击，拨开关不会误开抽屉。

**收起**：向下拖到一半或向下甩、点上方遮罩、或按返回键（返回键此时只收起抽屉，不退后台）。

**覆盖层语义**：抽屉画在操作页整页之上（**不是独立窗口**），遮罩只盖条身以上；收起态只有 56dp 条身贴底、面板整体在屏幕外。面板内容区高度 = 跟手行程，最多 460dp（装不下时取「可用高 − 56dp − 余量」），内容超长在面板内滚动。

关键常量：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `TX_DRAWER_STRIP_DP` | `56` | 收起态条身高度 |
| `DRAWER_PANEL_MAX_DP` | `460` | 面板内容区最大高度 |
| `DRAWER_FLING_VELOCITY` | `800f` | 甩动吸附速度阈值（px/s） |
| `DRAWER_SETTLE_MS` | `400L` | 收起后把面板滚动位置复位（`scrollTo(0)`）的延时 |

**展开后的面板内容**：

1. 目标信息：呼号 / 网格 / 频率 / 「取消目标」
2. 消息类型大按钮（2 行，FT8CN 六步）：`1 网格` / `2 报告` / `3 R报告` / `4 RR73` / `5 73` / `6 CQ`；点一下把该步报文填入「自定义」框
3. 自定义文本输入框：标签「自定义」、字符计数 `42/75`、清除 X
4. **CQ 前缀**：4×2 网格（**单选**，空串＝普通 CQ 显示「无」，长按编辑前缀文本）。选中的前缀由**所有 CQ** 使用（「消息类型 6 CQ」、抽屉「发送」的默认 CQ、自动程序发起的 CQ），报文形如 `CQ DX BG7ZJW OM89`；未选中任何非空前缀时仍是 `CQ BG7ZJW OM89`
5. 大发射按钮（52dp+）：显示待发摘要（有自定义文本＝该文本；有目标＝`应答 <呼号>`；否则＝`CQ <前缀> <我>`）；点按 = **本时隙剩余时间够播完整条报文（前导 + 波形自带保护间隔 0.5s + 报文时长）就立即发**，否则排下一个我方周期（FT8 报文 12.64s / 时隙 15s、FT4 报文 5.04s / 时隙 7.5s，故本时隙开头约 1.5s 都还来得及）；TX 时变红 + 倒计时，点按即停止
6. 「停止发射」按钮（整行，发射中可用）
7. 抽屉尾部「自动程序」行（摘要 + 设置…）与「同频 / 异频发射」两个互斥 Chip

> 原「4×2 宏（占位符模板）」与「发送队列（胶囊 / 加入队列 / 清空）」已**整体删除**：六步报文由第 2 项覆盖，前缀由第 4 项单选管理，`TxCompose.expandMacro` / `TxQueue` / `AppSettings.txQueue` 不再存在（`AppSettings.cqPrefixes` + `cqPrefixIndex` 取代）。

### 2.4 地图页

- 全屏深色底图，**无网格线图层**。底图是**离线 Web Mercator 卫星影像**（`assets/map/world_z5.jpg`，8192×8192，z5；按可见区域流式解码并乘 0.7 暗化，块缓存 LRU 有界，资产缺失时退回纯色矩形），投影由等距圆柱改为 **Web Mercator**（`MapProjection`）。
- **世界无缝循环**：视口状态只记中心的世界坐标 `(u,v)`（mod 1），**横向（经度）与纵向（纬度）都循环**，平移到任意方向都会从另一侧绕回来，无 ±180° 硬边；最小缩放仍是「整个世界适应窗口」。
- 所有叠加物（网格方块、呼号点、CQ 旗、我方台站、连线）统一用 `nearestCopy()` 取**离视口中心最近的一份**世界副本，同一目标在屏幕上只出现一次；`cellRect()` 让跨 ±180° 的方格不被撕成两半；底图块缓存与副本无关（跨缝不重复解码）。
- 网格标记：
  - **蓝**：该网格内有被解码到的信号（每次软件重启自动清除）。
  - **黄**：与该网格的电台完成过一次 QSO（读日志）。
  - **红**：该 QSO 的确认信息已收到（如 LoTW/eQSL，读日志）。
- 呼号标记：信号里**没有网格信息**时，用呼号前缀对应的归属地坐标立标（`Dxcc` 实体表，最长前缀优先），标记后带 `~` 表示「前缀近似」；同样按蓝/黄/红着色。
- CQ 旗帜：解码到 CQ 时在该位置立**红色旗帜**，可设置是否带呼号和信号强度。
- 信号连线：只显示**上一时隙**的连线，方向 `发方 → 收方`；线上有内容沿对应方向运动 —— 信号报告（`-12`/`+03`）显示数字、`73`/`RR73` 显示文字，其余载荷简化为**移动的方块**（开关可整体关闭文字）；**CQ 不连线**（只有发方，对端位置用红旗表示）。跨 180° 走**短弧**（`linkEnds()`，179°E ↔ 179°W 只画 ≈2° 短线）。
- 底部浮层：图例与统计 + 显示开关（CQ 呼号 / CQ 强度 / 连线文字）；右下角浮控：放大 / 缩小 / 回我的位置。
- 交互：**单击**呼号标记/CQ 旗 → 底部浮层显示详情（应答 / 日志 / 清除）；**操作页双击解码卡片** → 切到地图页并自动定位该呼号。

### 2.5 日志页

- 顶部：搜索（呼号/网格）+ 波段 + 模式 + 日期（区间对话框，UTC 闭区间，可只填一侧，支持 `YYYY-MM-DD` 与 `YYYYMMDD`）；存在任一筛选时出现「清除」chip。
- 表格化卡片：呼号 / 网格 / 时间 / RST / 模式；已确认（QSL/LoTW = Y）时左侧竖条变绿并显示 ✔。
- 交互：单击进「编辑通联」；**长按**弹「编辑 / 删除」菜单（删除二次确认）。
- 底部统计：QSO / DXCC / 网格 / 确认 四格 + 波段柱图。
- 「⋮」菜单：新增通联、导入 ADIF、导出 ADIF、清空日志（二次确认）。原「局域网后台地址」占位项已删除。

| **高亮与提醒** | 新 CQ 区域 / 新 ITU / 新 DXCC / 新网格 / 新前缀 / 新呼号 / 已通联（删除线·下划线·隐藏）/ 含我呼号哔声 / 末端标记（红=有我，蓝=正通联）；每个开关右侧有颜色小圆点，组尾有固定颜色图例 |
| **外观** | 暗 / 亮；字体小 / 中 / 大；瀑布高度 15% / **24%（默认）** / 45%；恢复布局（瀑布高度 / 字体）。原「瀑布配色」已删除 |
| **日志**（原「日志与网络」） | ADIF 路径（导入 / 导出）；清空全部记录。原 CloudLog / LoTW / eQSL 与局域网后台开关已删除 |
| **关于** | 版本号、GPL-3.0 许可与合规提醒 |

解码深度高级参数（每项在设置页都带一行作用说明；**默认值就是「快」预设**）：

- **时间 OSR**（1–4，默认 2）每符号时间细分数 → DT 分辨率 / 弱信号同步；*需重开接收生效*
- **频率 OSR**（1–4，默认 2）每 6.25 Hz 频率格细分数 → DF 估计精度 / 邻近信号分辨；*需重开接收生效*
- **最低得分**（4–40，默认 10）Costas 同步候选门限 → 调高更快但漏弱台
- **LDPC 迭代**（5–60，默认 20）纠错码最大迭代次数 → 调高弱信号解码率、更慢
- **候选上限**（20–500，默认 120）单时隙保留的同步候选数 → 调高给弱台更多机会、更慢
- **单时隙上限**（5–100，默认 100）单时隙最多输出的报文数 → 拥挤波段调大避免丢弃
- **减谱重解趟数**（1–4，默认 2）SIC 多趟减谱重解的趟数 → 1 = 关（单趟最快）；调高多挖同频弱台、耗时近似成倍（见 §5.4.2）
- **频率下限 / 上限**（默认 100 / 3000 Hz）解码搜索与瀑布显示范围 → 越窄越快；*需重开接收生效*
- **预设只有「快」**（默认，＝照搬 FT8CN「快速解码」，见 **Y2**）：一键把上面 7 项恢复默认值（**频率范围不随预设变化**）。
  想解得更全就**逐项调大**（LDPC 迭代 / 候选上限 / 单时隙上限最有效），改任一项预设自动变「自定义」。
  预设名由参数**反推**（不再单独持久化），因此只改频率范围不会变成「自定义」。

### 2.7 ⭐ 跟踪 CQ 列表面板

- 入口：操作页筛选条**最右的 ⭐**（角标 = 跟踪数量，点一次打开、再点或 ✕ 收起），与最左 🗑 对称。
- 列表是**呼号名单**（不是解码列表）：每个跟踪呼号带入本会话最近一次听到的网格 / 信号 / 时间，最近听到的排前面。
- 手势：**左滑 = 呼叫该呼号**；**右滑 = 取消跟踪**（该行随即消失）。
- 空态：「还没有跟踪的呼号。开启「自动跟踪 CQ」会自动加入；也可长按解码 →「跟踪」。」
- 数据来源：`AppSettings.followCalls`。两个来源：解码列表长按「跟踪」手动加入；「自动跟踪 CQ」开着时把本波段未通联的 CQ 台自动写入（`FollowRoster`，见 `docs/QSO.md` §5.1）。**不参与显示过滤**，只作为自动程序的输入（「自动跟踪 CQ」关掉时，名单里 CQ 台的 CQ 仍会被自动呼叫）。
- **通联完成后自动移除**该台（**有意偏离 FT8CN**：其名单不会自动变动）。

### 2.8 自动程序弹窗

- 入口：顶栏菜单「自动程序」、发射抽屉「自动程序」行、设置页 6.3，三处为**同一套面板**（`AutoProgramPanel`）。
- 口径（**照 FT8CN 单档**，取代旧的 AutoSeq 等级 0–4 与「手动/主叫/混合」档位）：**没有工作模式档位、没有启用确认框**；打开「发送总开关」即启用自动程序。
- 面板四项：
  - **发射监管**（0 / 5 / 15 … 95 分钟，默认 10，`0` = 不监管）：连续发射超时后自动**关闭发送总开关**（不是切模式）。
  - **无回应次数**（0–30，默认 0 = **FT8CN 的内置 20 个批次硬上限**）：判据只在**我发过 RR73、正等对方 73** 时生效；超限后放弃当前目标 —— 优先换到别的 CQ 台，没有就自己发 CQ。
  - **自动跟踪 CQ（本波段）**（默认开）：把关哪些 CQ 台能进自动候选（本波段还没通联过即可），并把这些台**自动写进 ⭐ 跟踪列表**（有意偏离 FT8CN；通联完成后自动移除）。
  - **自动呼叫 CQ 台**（默认开，总闸）：关掉后只回应定向呼叫、自己发 CQ。
- 排版：弹窗内面板自带内层滚动（高度封顶 460dp）；设置页内嵌版 `nestedScroll = false`，面板**完全展开、跟随整页滚动**（不再套第二层滚动条）。

## 3. 交互约定

### 3.1 解码卡片手势

- **单击**：底部弹 Half-sheet 详情（距离、方位、网格、强度曲线；按钮：呼叫 / 日志 / 备注）。
- **双击**：跳地图页定位。
- **长按**：菜单 —— 呼叫 `<呼号>` / 回复 `<呼号>`（按报文类型自动决定发什么）/ 查看日志（跳日志页并预填该呼号）/ 复制消息 / 跟踪（切换为取消跟踪）/ 忽略。
- **左滑**：**设为目标并呼叫**该台（露绿色「呼叫」条）—— 直接把红线移到该条频率、把发射时隙对到对方时隙的相反周期并交给第 3 层接管；**没有任何确认框**，唯一闸门是「发送总开关」。本时隙来得及就本时隙发。
- **右滑**：**删除该条**（露灰色「删除」条）；在「跟踪」视图里右滑 = 取消跟踪该呼号。

### 3.2 ⭐ 列表手势

- **左滑 = 呼叫**该呼号（顶栏目标区 / 发射抽屉随即显示该呼号，并在下一时隙起发）。
- **右滑 = 取消跟踪**该呼号（该行随即消失）。

### 3.3 筛选条

- 构成：**🗑 / chip / 🔍 / ⭐**。
- `DecodeFilterTag` 现为 `ALL / TO_ME / CQ / REPLY / SEVENTY_THREE / WORKED`（标签：全部 / 与我有关 / CQ / 回复 / 73 / 已通联）。
- `ALL` **互斥**其余项；选中其余任意项会自动取消 `ALL`，其余项之间为**多选并集**；一个都没选 → 列表显示空态提示「请至少开启一个筛选」。
- 🗑「清除解码信息」只清**显示**列表，不写日志、不改「已解码时隙」计数、不影响自动程序（自动程序用的是自己每时隙的 `pendingDecodes` 批）。

### 3.4 自动翻到最新

- 列表保持「新→旧、最新在上」；每批新解码到达时自动回到最新（无需手动上滑）。
- 用户一旦手动拖动即暂停跟随（不清屏、不打断阅读）；把列表滑回**顶部（index 0）**后自动恢复跟随。手指正在拖动时不抢滚动。

### 3.5 发射频率（红线 + 占用带宽红条）/ 同频异频

- 瀑布上**单击或水平拖动**即把红线（**发射频率 = 报文下边频**）移到按下/拖动处，右下角 `TX xxxx Hz` 随之更新、重启后保留；**没有绿色「接收频率」竖线**。
- 红线右侧的**半透明红条**标出整条报文实际占用的带宽 `[f, f + 50 Hz]`（FT8；FT4 约 83 Hz）：红线是**下边频**、条右缘是**上边频**，用来判断会不会压到别人的信号（见 §2.3.1）。
- **长按**瀑布：先把红线移到按下处，再打开最近一条解码的详情。
- **同频发射**（默认）：选台（点解码行 / 应答 CQ / 自动程序选到目标）时红线跟到对方频率（「点谁打谁」）。
- **异频发射**（split）：红线固定不动，选台不改发射频率。
- 抽屉「自动序列」两个互斥 Chip 与设置页「同频发射」开关同步、持久化；两种情况发射都取红线位置。

### 3.6 发射闸门

- 全 App **不再有任何「确认发射」弹窗** —— CQ / 应答 / 解码卡片左滑 / 详情面板「呼叫」/ 地图页呼号标记「应答」/ 抽屉「发送」**都是点下即排程**（顶栏第 3 行随即出现待发 / 发射中）。
- 唯一闸门是**「发送总开关」**（关 = 只接收，开 = 允许发射；仅会话内有效、不持久化，故每次启动都默认只接收）。总开关为关时 `startCq()` / `answer()` 直接返回并提示需先打开总开关，因此删掉二次确认不会误发。
- 自动程序：**打开「发送总开关」即启用**，也没有启用确认框。
- 另有常驻的「停止发射」与紧急中止（`abortTx()`，非阻塞、无锁，可在 UI 线程调用）。

### 3.7 返回键

- **接收中**：退到后台继续接收（前台服务保活），并弹一条短提示；**未接收时**保持默认行为退出。
- 发射抽屉 / 弹窗打开时，返回键先收起它们（各自处理，不退后台）。

### 3.8 禁止频谱缩放

- 频率轴固定铺满 `fMin–fMax`，**不做缩放 / 平移**（原双指捏合缩放已去掉）。

### 3.9 发射抽屉跟手拖动

- 按住收起态条身上拖即**跟手展开**（面板从条身下方露出）；松手按「拉过一半 / 甩动 ≥ `DRAWER_FLING_VELOCITY`」吸附。
- 展开后条身即抽屉顶部手柄：向下拖 / 下甩 / 点遮罩 / 返回键收起。
- 常量：`TX_DRAWER_STRIP_DP = 56`、`DRAWER_PANEL_MAX_DP = 460`、`DRAWER_FLING_VELOCITY = 800f`、`DRAWER_SETTLE_MS = 400L`。

## 5. JNI 契约

本文档定义 Ft8Vox 中 Kotlin 与 native（`libft8.so`）之间的接口约定。阶段 2–4 的实现以此为准，避免音频、UI 与引擎反复返工。

### 5.1 命名与符号

- Kotlin 入口类（均为 `object`，位于 `com.example.ft8vox.engine`）：
  - `Ft8Engine`：离线解码 / 编码。
  - `AudioEngine`：实时音频 I/O 与时隙调度。
- native 函数符号必须遵循 `Java_<包名下划线>_<类名>_<方法名>`。
  - 例：`Ft8Engine.test()` → `Java_com_example_ft8vox_engine_Ft8Engine_test`。
- **重命名类或包时，必须同步修改 `app/src/main/cpp/jni_bridge.c` / `audio_engine.c`。**
- 这些 JNI 类/方法必须在 `app/src/main/keepRules/rules.keep` 中保留（防 release 混淆）。

### 5.2 数据格式约定

| 项 | 约定 |
| --- | --- |
| PCM 格式 | 单声道、`float32`、取值范围 `[-1.0, 1.0]` |
| 分析采样率 | **12 kHz**（FT8/FT4 标准） |
| 采集采样率 | 设备原生（常见 48 kHz），由 native 重采样到 12 kHz |
| 大数组传递 | **`FloatArray`**（`GetFloatArrayElements` 读取，块间无拷贝） |
| 文本编码 | UTF-8（报文为 ASCII 子集） |
| 协议 | 枚举 `Protocol { FT8, FT4 }` |

> 解码核心（monitor + 呼号哈希 + 候选/解码）已抽取为 native 模块 `ftx_session.c`，
> 离线（`jni_bridge.c`）与实时（`audio_engine.c`）两条路径共用。

### 5.3 生命周期接口（Ft8Engine，离线）

| Kotlin 方法 | 职责 | 线程 |
| --- | --- | --- |
| `initialize(config: Ft8Config, decodeParams: DecodeParams = DecodeParams())` | 创建并初始化 monitor/waterfall（协议、采样率、频率范围、过采样率），并下发解码参数 | 初始化线程 |
| `setDecodeParams(params: DecodeParams)` | 更新**热生效**的解码参数（见 5.4.1），无需重建引擎 | 任意（内部无锁读写单字） |
| `reset()` | 清空当前时隙的 waterfall 与分块缓冲，准备下一周期 | 解码线程 |
| `release()` | 释放 native 资源 | 与 initialize 同线程 |

`Ft8Config` 字段（对应 `monitor_config_t`）：`protocol`、`sampleRate`、`fMin`、`fMax`、`timeOsr`、`freqOsr`。
**改动 `Ft8Config` 需重建引擎**；`DecodeParams` 则可在运行中调整。

### 5.4 解码接口

| Kotlin 方法 | 职责 |
| --- | --- |
| `processAudio(samples, length)` | 接收任意长度的 12 kHz PCM；native 内部按 monitor 块大小累积，余数留待下次（支持流式分块喂入） |
| `decodeDetailed(): List<DecodeResult>` | 时隙结束时调用，执行候选查找 + 解码，返回带指标的报文列表 |
| `decode(): List<String>` | 便捷方法，等价于 `decodeDetailed().map { it.text }` |

`DecodeResult` 字段（对应 native `ftx_decode_result_t`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `text` | `String` | 解码出的报文明文 |
| `snr` | `Int` | 近似 SNR（dB，换算到 2500 Hz 参考带宽） |
| `dt` | `Float` | 相对时隙起点的**名义**时间偏移（秒），已减去 0.5 s 起始延迟 |
| `df` | `Int` | 音频频率偏移（Hz） |
| `score` | `Int` | 候选 Costas 同步得分 |
| `slotUtcMs` | `Long` | 所属时隙的 UTC 起点（毫秒）；离线解码为 0 |

> `DecodeResult` 由 native 直接 `NewObject` 构造，构造签名固定在 `jni_common.h`：
> `(Ljava/lang/String;IFIIJ)V`。**修改 Kotlin 字段顺序/类型时必须同步更新该签名。**

SNR 估算口径（照搬 JTDX，与 WSJT-X 同一尺度）：对每个符号 i，取**该符号实际发送音调**所在 bin 的功率 `P_sig`（含信号 + 本底噪声），
与**同一符号内其余音调** bin 的平均功率 `P_noi`（只含噪声）之比 `r_i = P_sig / P_noi`；
在**功率域（线性域）** 对全部符号求平均得到 `mean_r`，扣除信号 bin 内自身的本底噪声得 `excess = mean_r − 1`，
再按 `snr = 10·log10(excess) − 26.5 + window_db` 折算到 2500 Hz 参考带宽（FT8：79 符号；FT4：105 符号），最后钳位。
噪声参考取算术均值、**不使用分布假设**，且与被测信号同符号、频率紧邻，天然抗带内强台与时间起伏。

> **为何换掉旧口径**：旧版取「信号两侧局部窗口（`±16 bin`，约 ±100 Hz，排除音调区间 `freq_offset-2 .. freq_offset+9`）的 **25 分位**，
> 再按 bin 功率服从指数分布 `÷ −ln(0.75)` 换算回均值」。该换算**只在理想白噪声下无偏**；
> 真实电台音频常见的脉冲/结构化噪声会让分位远低于均值 → 噪声底被低估 → **SNR 系统性虚高**。
> 注意 harness 用的正是理想白噪声，恰好是旧口径的适用边界，故其自测通过并不能证明旧口径在真机音频上无偏。

> **照搬原式的已知代价（本项目瀑布窗的限制）**：JTDX 的分析窗是 **1 个符号 + 矩形加权**，8 个音调在窗内**严格正交**，
> 其余音调 bin 确实只含噪声。本项目瀑布窗是**周期 Hann、窗长 = 1 符号周期 × freq_osr**（默认 `freq_osr=2`，约 2 个符号），
> 音调不再正交，其余音调 bin 会被**信号自身的泄漏**污染。泄漏比例很小（约 −31 dB，即信号功率的 0.08%），
> 但强台的 bin 信噪比可达 +35 dB，泄漏因此达噪声底的数倍，会把噪声底抬高，使读数随信号增强而**压缩**：
> `excess_meas ≈ (S/N) / (1 + α·S/N)`（`α·S` 为泄漏功率），弱台基本无偏、强台偏低。上表已量化该压缩（真值 ≥ −5 dB 时偏差 4~8 dB）。
> 若要消除这段压缩，只需把噪声窗口挪到音调区间之外（提交 `ba8a189` 保存了该替代实现）。

经验修正两项（对应 JTDX 的「经验曲线 + 钳位」）：

1. **去偏**：噪声参考是 n 个指数分布 bin 的**平均**，`E[1/mean_n] = n/((n−1)·N)`，比真值大 `n/(n−1)` 倍（FT8 `n=7` → `+16.7%`），
   故逐符号乘回 `(n−1)/n`；不加此项弱台会整体偏高。
2. **窗函数折算**：`window_db = 10·log10(RBW / 2500) + 26.5`，其中 `RBW = 1.5 · (1/符号周期) / freq_osr`
   （分析窗长 = 1 个符号周期 × `freq_osr`，周期 Hann 窗噪声等效带宽为 1.5 个 FFT bin）。
   与 JTDX 的 1 符号矩形窗（≈6.25 Hz）不同，故用该项把 `−26.5` 的基准换到本项目窗的等效噪声带宽；
   `freq_osr=2`（当前默认「快」）时 `RBW = 4.6875 Hz → window_db = +0.77`，**净折算 = 10·log10(RBW/2500) = −27.27 dB**，与 WSJT-X 的 `−27.0` 一致。
   > 若写死 `−27.0`：`freq_osr=1` 会**偏低约 2.7 dB**、`freq_osr=4` 会**偏高约 3.3 dB**；FT4 亦按同一 RBW 公式处理。
   > 常数定义在 `ftx_session.c`：`JTDX_SNR_CAL_DB 26.5`、`JTDX_SNR_MIN_DB −24`、`JTDX_SNR_MAX_DB +40`。

**实测校核（合成信号，白噪声，同一份数据对照 `HEAD` 旧实现）**：以「真值」`SNR = P_tone/(N0·2500)` 为准，

| 真值 | −20 | −15 | −10 | −5 | 0 | +5 | +10 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 旧（p25 局部窗口） | −21.29 | −15.48 | −11.32 | −6.54 | −1.20 | +3.85 | +8.34 |
| 新（照搬 JTDX 原式） | −21.79 | −16.42 | −12.62 | −9.35 | −6.28 | −2.76 | +2.39 |
| 对真值偏差 | −1.8 | −1.4 | −2.6 | **−4.4** | **−6.3** | **−7.8** | **−7.6** |

即**弱台（≤ −20 dB）几乎不变，强台被压缩 4~8 dB**（原因见上「已知代价」；`matchedRect_t4` 等独立对照支路可证明真值列无偏）。
强台场景（弱台真值 −15 dB + 1000 Hz 处带内强台）：旧「全带均值」在强台 ≥ +20 dB 时被压到 −24 dB 下限，新实现稳定在 −20 ~ −21 dB。
若真机对比仍偏高，优先排查**采集链路**而非公式：
① AAudio 采集预设（见 §5.6，已强制 `UNPROCESSED`，避免系统降噪把噪声底压掉）；
② `fMin/fMax` 设得比实际音频通带更宽时，噪声底会被安静频段拉低 → SNR 虚高。

> 参考：WSJT-X `ft8b.f90` 用 `xsig/xnoi − 1`（单 bin 噪声）与默认支路 `xsnr2 = xsig/xbase/3.0e6 − 1`
> （`sbase` 为 `baseline.f90` 拟合的**局部**噪声基线），其提交说明亦强调「带内强台不应把弱台判低」。

说明：呼号哈希表由 **native 侧管理**（去重、老化），不通过 JNI 回调，避免频繁跨语言调用。

#### 5.4.1 可调解码参数（`DecodeParams` ↔ `ftx_decode_params_t`）

| 字段 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- |
| `minScore` | 10 | 4..40 | Costas 同步最低得分，越高候选越少越快 |
| `maxCandidates` | 120 | 20..500 | 单时隙候选上限 |
| `ldpcIterations` | 20 | 5..60 | LDPC 最大迭代次数，越高越慢、弱信号解码率越高 |
| `maxDecoded` | 100 | 5..100 | 单时隙最多解出的报文条数 |
| `passes` | 2 | 1..4 | 多趟减谱重解（SIC）趟数；1 = 关闭（单趟），2 = 默认。见 §5.4.2 |

> 上表「默认」是 **JNI 结构体 `DecodeParams` 的构造默认值**，只在下发设置前的极短窗口内生效；
> **App 实际下发的是设置页的值**，其默认（＝「快」预设，**照搬 FT8CN「快速解码」**，见 **Y2**）为
> `minScore` 10 / `ldpcIterations` 20 / `maxCandidates` 120 / `maxDecoded` 100 / `passes` 2，
> 另有 `timeOsr`/`freqOsr` = 2、`fMin`/`fMax` = 100 / 3000 Hz。

- 这些参数**只影响搜索与 LDPC 迭代，不改变 STFT 结构**，因此可在接收过程中热更新（`setDecodeParams`）。
- native 侧 `sanitize_decode_params()` 会再次钳制；候选/结果数组按上限（512 / 128）静态分配，调参不会改变内存占用。
- 与 `monitor_config_t`（`fMin`/`fMax`/`timeOsr`/`freqOsr`）不同：后者改动需重建引擎（重启接收）。
- 设置页**只有一个预设「快」**（＝ `AppSettings.decode` 的默认值）；原「标准 / 深」两档已删除，
  想更全就逐项手改，预设名自动变「自定义」（由参数反推，`decode_preset` 键不再读写）。
- `passes`（SIC 趟数）**从设置页「减谱重解趟数」下发**（JNI 第 5 个参数，默认 2、范围 1–4）；
  与其余 5 项一样归「快」预设管：手改成 1/3/4 即显示「自定义」。native 仍保留「0 → 2 趟」的兜底，
  供只填前 4 个字段的旧调用方使用。

#### 5.4.2 多趟减谱重解（SIC）

单趟解码只能看到「最强的那一层」。在官方 60 个测试音频（`app/src/main/cpp/ft8_lib/test/wav`，
期望 1298 条）上实测：候选数 120→500、LDPC 20→60、`minScore` 10→4、过采样 2/2→2/4 或 4/4，
**合计一条都不涨**；把「期望里有、我们没解出」的 369 条做分类，得：

| 缺失原因 | 条数 | 占比 | 对策 |
| --- | --- | --- | --- |
| 与某条已解出报文**同频**（相距 0~3 Hz） | 266 | 72% | 减谱重解（本节） |
| 孤立弱信号（灵敏度不足） | 94 | 25% | 需更强解码器（本版无 OSD，暂无解） |
| 同内容重复（按内容去重合并） | 9 | 3% | 有意为之 |

实现（`ftx_session.c` 的 `sic_subtract_message()` + `ftx_session_decode()` 的多趟循环）：解完一趟后，
对每条已解报文用它的 `payload` 重新编码出**真实音调序列**，逐符号只把该符号实际占用的那 1 个音调
bin「抹平」到该处的最低幅度，得到「残留谱」；在残留谱上重新搜候选、再解一趟。三个坑（都实测踩过，
故参数写死在代码里）：

1. **不能把整段 8 个音调 bin 一起抹平**：同频伙伴正住在这段带宽里，会被一起毁掉——60 个音频合计一条不多解。
2. **不能置零**：sync 得分是「相邻 bin 相减」的差值指标，置零会凿出深坑，坑沿的「实测值 − 0」造出
   比真信号还高的假分（实测假分 74 vs 真信号 32），候选名额被占光。压平到本地最低幅度不产生边沿。
3. **「本地最低幅度」的窗口取 ±1 bin（共 4 个 bin）最好**；取整个 8 音调带宽反而更差。

效果与代价（60 个测试音频，模拟器 x86_64）：

| 趟数 | 解出 | 耗时（最忙文件） |
| --- | --- | --- |
| 1（关闭） | 956 | 11~15 ms |
| **2（默认）** | **989（+33 / +3.5%）** | **19~21 ms** |
| 3 | 989（不再增长） | 28~37 ms |

- 21 个文件有增益、**零回归**；+33 条中 32 条在期望清单内（真报文）；另 1 条属「我们解出但参考
  清单没有」的那一类，该类单趟时本来就有 27 条（2.8%），**比例不变**（即 SIC 未抬高假解码率）。
- **已知边界**：本实现只减幅度、不重建相位（不是时域相干相减）。合成用例显示：两条信号同频、或
  相差 1~2 个音调 bin 且强度差 12~28 dB 时，强信号在弱信号音调 bin 上的相干泄漏抹不掉，仍解不出
  ——要吃掉那部分缺口需要 WSJT-X 式的时域相减（`WATERFALL_USE_PHASE` + 波形重合成 + 逐趟重做
  STFT），内存 ×8、工作量远大于本节。语料里 +33 条属于「串扰较轻」的那一类。
- FT4 走同一实现（`ft4_encode` + 4 音调 + `FT4_NN`）；官方语料无 FT4 素材，仅以合成单信号用例
  验证过「不破坏 FT4 解码」。

### 5.5 编码接口

| Kotlin 方法 | 职责 |
| --- | --- |
| `encode(text, frequencyHz, protocol, sampleRate): FloatArray` | 文本 → 77-bit 载荷 → tone → GFSK 波形，返回**一个完整时隙**的 12 kHz PCM（含首尾静音填充） |

实现约定：

- **采集**：请求 `preferredRate`（优先 48 kHz），native 重采样到 12 kHz。
  降采样先过 **4 阶 Butterworth 低通**（截止约 `0.35 × outRate`，抗混叠），再线性插值；升采样直接线性插值。
- **采集预设（绕开系统语音处理）**：AAudio 输入预设默认就是 `VOICE_RECOGNITION`（部分机型带降噪/AGC），
  会压低噪声底（SNR 虚高）并吞掉弱信号。故按 `UNPROCESSED → VOICE_RECOGNITION → GENERIC` 依次回退，
  成功即用（日志打印实际预设）。`setInputPreset` 自 API 28 才提供，minSdk 26/27 上用 `dlopen` 解析符号，
  解析不到则保持系统默认。
- **时隙调度**：按 UTC 对齐（FT8 = 15 s，FT4 = 7.5 s）。仅在时隙起点后 200 ms 内开始采集，累积满 `slot_samples` 后解码；若跨入下个时隙则先解码已采集部分并重新对齐。
  时隙边界判定用的是 `utc_now_ms() - slot_offset_ms`（见 5.6.3「时隙偏移」），因此 `setSlotOffsetMs` 会把**整个采集窗口**平移；上报的 `slot_start_ms` 仍是名义 UTC 时隙起点，时隙序号与 0/1 奇偶不受偏移影响。
- **线程**：AAudio 回调只写入无锁 SPSC 环形缓冲（不分配、不加锁）；DSP 线程负责重采样与解码。
- **限流**：环形缓冲满时丢弃样本并累加 `droppedSamples` 统计。
- **waterfall 行流**：每处理完一个 monitor block，将 `time_osr` 行（取 `freq_sub=0`）写入 native 环形缓冲；
  FT8 下约每 80 ms 一行。Kotlin 侧用 `pollWaterfall()` 拉取，若落后太多则自动丢弃被覆盖的旧行。
- **发射时序（Kotlin 侧调度，不新增 native 线程）**：`playTx()` 是阻塞写，由 Kotlin 轮询线程按时隙触发：
  1. 操作者确认（防误发）后先 `startPlayback()` 建好播放流，避免发射瞬间才建流而错过时隙；
  2. 每 80 ms 检查一次，计算目标发射时隙与播放起点（见 5.6.1）：无前导时就地在「当前时隙奇偶 == 我方发射周期」且起点后 **1200 ms** 内发射；有前导时提前 `PTT 延迟 + 前导音时长` 启动，使 FT8 数据仍落在时隙起点。同一时隙绝不重复写；
  3. 迟到时按迟到量缩短前导（`effectivePreambleMs`）以保持数据对齐；迟到超过 `前导 + 1200 ms` 则放弃本时隙；
  3a. **QSO 进行中必须等到上一时隙的解码处理完再排定本时隙**（`lastDecodedSlotIndex` 闸门，
     见 `docs/QSO.md` §2）：native 的 14.88 s 解码窗口比前导提前量晚，抢发会把旧报文发出去、
     把新报文挤到下下个周期（「RR73 没回 73」「别人呼叫我我却在发 CQ」）。等待期间不写播放流，
     解码到手后走「就地发射」；若解码改判了报文，同一时隙仍能发（各 `*Internal` 会复位槽位标记）；
  4. 发射波形自带 0.5 s 前导静音，用于吸收「上一接收时隙解码完成 → 决定本轮报文」的数百毫秒延迟；
  5. 其余时间不向播放流写数据（保持静音）；紧急停止用 `abortTx()`（无锁、非阻塞，见 5.6.4），
     `stopPlayback()` 只用于 `stop()`/`release()` 关流释放设备。

#### 5.6.1 VOX / PTT（U7b）

无 CAT 时 App 无法直接控制电台 PTT，只能通过发射音频序列间接键控。`VoxConfig` 字段：

| 字段 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- |
| `pttDelayMs` | 0 | 0..500 | 数据前的前导静音（留给声卡路由/电台起键） |
| `leadToneMs` | 0 | 0..2000 | 数据前的前导单音（1 kHz），用于抢先键控 VOX |
| `watchdogMs` | 10000 | 1000..60000 | 发射写入看门狗（卡死保护） |

- **输入电平读数**：native 在 DSP 线程对原始输入块计算 RMS 电平（快攻击/慢释放平滑）并暴露为
  `voxLevelDb`（下限 `VOX_LEVEL_FLOOR_DB`）。**纯显示用**（观察输入、校准 5.6.2 的「输入增益」），
  **不做任何触发判定、不参与发射门控**（发射仍按时隙）。
  2026-09-26 前曾有一套「VOX 触发（音频/静音检测）+ 阈值 + 去抖」判定与「触发/空闲」指示，
  已按用户要求整体删除（无 CAT 时该判定只是对输入音频活动的近似，徒增误解）。
- **前导与对齐**：`playTx()` 把 `pttDelayMs` 静音与 `leadToneMs` 单音插在数据之前；调用方（`planTx`）相应提前播放起点，保证数据落在时隙起点。
- **看门狗**：`write_blocking()` 以「本段音频预期播放时长 + 3 s」为实际阈值（不低于 `watchdogMs`），避免截断合法的整时隙发射；仅在音频设备卡死时中止写循环。
- `nativeSetVox(handle, pttDelayMs, leadToneMs, watchdogMs)` 只下发 PTT 三项。
- `nativeGetState` 返回 11 个 `Long`：索引 0–9 同前，`[10]=vox_level_db×10`。

#### 5.6.2 音频路由与增益（U7c）

- **设备枚举（Kotlin，`engine/AudioDevices.kt`）**：用 `AudioManager.getDevices(GET_DEVICES_INPUTS/OUTPUTS)` 列出设备，返回 `{id, 名称, 类型标签}`；首项恒为「系统默认」（id 0）。设备 id 即 `AudioDeviceInfo.getId()`，与 AAudio `setDeviceId` 使用同一编号。
- **路由**：`startCapture(preferredRate, deviceId)` / `startPlayback(preferredRate, deviceId)` 在 `deviceId > 0` 时调用 `AAudioStreamBuilder_setDeviceId`；`<= 0` 走系统默认。设备选择只在**建流时**生效：
  - 输入设备变化需重开采集流（运行中提示「下次开始接收生效」）；
  - 输出设备变化时 `stopPlayback()` 关闭旧流，下次发射用新设备重开（发射中提示「下次发射生效」）。
- **采集增益**：`nativeSetInputGain(handle, gainDb)` 钳制 −12..30 dB，DSP 线程对原始采集块乘 `10^(dB/20)`，超过满幅限幅到 [−1,1] 防回绕。增益作用于**含输入电平计算**的整条链路，故调增益会同时改变状态栏的电平读数。
- **输出音量**：`nativeSetOutputGain(handle, gainDb)` 钳制 **−30..0 dB**，在 `write_blocking()` 写入声卡前对**整段播放缓冲**原地乘 `10^(dB/20)`（前导静音/前导音/FT8 报文/测试音一视同仁），超过满幅限幅到 [−1,1] 防回绕。**只能衰减**：发射波形由 `synth_gfsk()` 合成、本身已是数字满幅（`sinf()`，峰值 1.0 ≈ 0 dBFS），放大只会削顶并破坏频谱；0 dB = 原样输出（默认）。改设置后**下一次播放**生效。
- **设备 id 易变**：设备 id 可能随插拔/重启变化，存的是原始 id 字符串（空串=默认），失配时 `label` 回退「系统默认」。

#### 5.6.3 时隙偏移（U7「发射偏移」，整时隙校准）

- **语义**：`setSlotOffsetMs(offsetMs)` 把**整个时隙网格**平移（正 = 推后，负 = 提前），
  native 侧只影响 `feed_slot()` 的边界判定（→ 采集窗口起点），Kotlin 侧由 `planTx(..., slotOffsetMs)`
  把发射起点按同一值平移。两处共用同一个 `slot_offset_ms`，因此「解码窗口」与「发射起点」永远同步。
- **校准用法**：解码卡片显示的「时间差 DT」即对端信号相对本机窗口起点的偏移（名义 0.5 s 基准，
  `out->dt = time_sec - 0.5f`）。把该值原样下发（`+1.5s` → `+1500`）后，后续解码 DT 应回到约 0，
  同时我方发射也落到对端的时隙起点上；负 DT 填负值同理。
- **范围**：钳制 ±2500 ms。上限来自解码器的搜索窗 —— `ftx_find_candidates` 的
  `time_offset ∈ [-10, +19]` 个符号块，FT8 符号 0.16 s → 相对窗口起点约 `[-1.6, +3.04]s`
  （DT 约 `[-2.1, +2.5]s`）；**FT4** 符号仅 0.048 s，搜索窗约 ±0.5 s，偏移过大（尤其正向）会解不出。
- **口径不变**：`slot_start_ms`、时隙序号、0/1 奇偶、「双方相反周期」判定全部仍按名义 UTC 时隙，
  本偏移只在时隙内部平移起点（`|offset| < 7.5 s` 时不跨时隙）。热生效；改在时隙中途时当前窗口会
  错位到下一个网格点才稳定（属预期）。

#### 5.6.4 播放/关流的线程安全（防 use-after-free + 防主线程 ANR）

`playTx()` / `playTone()` 是**阻塞写**，`write_blocking()` 会长时间卡在 `AAudioStream_write`。
而 `stopPlayback()` / `nativeDestroy()`（换协议重建引擎、Activity 销毁）随时可能在另一线程执行 ——
若直接 `AAudioStream_close` / `free(引擎)`，写入线程就会踩到已释放的 AudioTrack 共享缓冲
（真机 tombstone：`libaudioclient AudioTrack::write` ← `libaaudio AudioStreamTrack::write`
← `nativePlayTx` ← `AudioEngine.playTx`）。约定：

- **必须分块写**：`AAudioStream_write` 对阻塞流会**一直等到请求的帧数全部写完**才返回
  （`timeout` 只在设备卡死时兜底）。若一次请求剩余全部帧，写线程会**整段发射独占 `tx_mutex`**
  （FT8 约 16 s、FT4 约 5.5 s），同进程的关流方（尤其是 UI 线程）会被卡满整段 → **ANR**。
  故 `write_blocking()` 每次最多写 `TX_WRITE_CHUNK_FRAMES`（4096 帧，48 kHz 约 85 ms），
  每块之间释放锁并重查代次。
- **只在持有 `tx_mutex` 时碰 `out_stream`**：写入线程每次 `AAudioStream_write` 前后都持锁；
  单次写入超时 0.5 s，保证关流方最多等这么久就能拿到锁。
- **`out_gen` 代次**：`nativeStopPlayback`/`nativeStartPlayback`/`nativeAbortTx` 都会 +1；
  写入线程进入时记下代次，一旦发现代次变了（或 `out_stream == NULL`）立即返回**已写入帧数**
  （主动中止不算失败）。
- **`abortTx()`（UI 线程「停止发射」专用）**：只做 `atomic_fetch_add(&e->out_gen, 1)`，
  **不加锁、不关流**，因此调用者永不阻塞；写入线程最迟在下一块边界（约 85 ms）退出，
  已进 AAudio 缓冲的少量音频（≤ 一个缓冲，几十毫秒）自然播完。不关流也避免与后续
  `startPlayback()` 抢流（旧实现在 UI 线程 `stopPlayback()` → 卡死 → ANR）。
- **`tx_active` 播放调用计数**：`nativePlayTx`/`nativePlay`/`nativePlayTone` 进入即 `tx_enter()`、
  退出前 `tx_leave()`；`nativeDestroy` 先 `tx_stop_and_close()` 再 `tx_wait_idle(3000ms)`，
  **只有确认没有播放调用在用引擎才会 `free`**，否则宁可泄漏这点内存也不崩（日志会打
  `engine leaked to avoid use-after-free`）。
- **Kotlin 侧四件事**：
  1. `AudioEngine.handle` 是 `@Volatile`；`release()` **先清零句柄再 `nativeDestroy`**，
     销毁期间新起的 JNI 调用只会拿到 0 而被拒绝。
  2. 轮询（`Dispatchers.Default`）不受 native 播放保护：`SessionViewModel.stopPollingAndJoin()`
     在 `stop()`/`onCleared()` 里 `cancel()` + `join()`，等它从 `pollDecoded()/state()` 返回后才销毁引擎。
  3. 引擎重建会 +1 一个 `engineGen`：排好队的发射协程带着旧代次，发现自己过期就**丢弃本次发射**
     （`txJob.cancel()` 打断不了已开始的 JNI 阻塞写），避免把旧协议波形发到新引擎上。
  4. 中止发射会 +1 一个「发射作废代次」`txAbortGen`（`SessionViewModel.abortTransmit()`）：
     排好队但还没落盘的发射协程发现代次变了就丢弃，避免「已按停止，却又响一整段」。

### 5.8 线程模型

- **AAudio 回调线程**：只把 PCM 写入无锁 SPSC 环形缓冲，绝不调用重 JNI、加锁或分配内存。
- **DSP/解码线程**：从环形缓冲取数据 → 重采样 → 按块累积 waterfall → 时隙结束解码，结果进入待轮询队列。
- **发射线程**：调用 `encode` 生成 PCM，`play()` 内部重采样后阻塞写入 AAudio 播放流。
  - 与「关流/释放引擎」互斥，见 §5.6.4：`tx_enter/tx_leave` 计数 + `out_gen` 代次 + 只在持
    `tx_mutex` 时读 `out_stream`；写循环按块（`TX_WRITE_CHUNK_FRAMES`）释放锁。同一条规则保护
    `playTone()`（设置页「测试音」）。UI 线程中止发射走无锁的 `abortTx()`，关流只发生在
    `stop()`/`release()`。
  - Kotlin 侧：`stopPollingAndJoin()` 保证销毁引擎前轮询已退出；`engineGen` 丢弃跨引擎的迟到发射；
    `txAbortGen` 丢弃「已按停止」的迟到发射。
- native 对象（monitor 等）与创建/使用它的线程绑定；若跨线程调用 JNI 需 `AttachCurrentThread`。
- MVP 阶段解码结果**拉取返回**，不引入 native → Kotlin 回调。

### 5.9 错误处理

- 参数非法（采样率、频率范围、协议）在 `initialize` 时校验并抛出异常。
- 解码失败（LDPC/CRC 未通过）不抛异常，仅不产生结果；调试信息（`ldpc_errors`、CRC）通过日志输出。
- `startCapture` / `startPlayback` 失败返回负错误码而非崩溃，UI 据此提示（如模拟器无音频设备）。
- native 崩溃需最小化：所有输入数组长度先校验再访问。

#### C. 真实通联（**核心验收**）

- [ ] 与对端约定：同一波段、同一协议（FT8/FT4）、相对周期（我偶他奇或反之）。
- [ ] **周期必须相反（关键）**：对端在第 1/3 个时隙（偶）发 CQ 时，我自动发在第 2/4 个（奇）；对端在奇时我发偶。双方**绝不同周期发射**。
- [ ] **标准节奏**：`CQ → 应答 → 报告 → R报告 → RR73` 依次落在**相邻时隙**（约 75 s 完成整段），而不是每条都白等一个周期。
- [ ] 展开操作页底部发射抽屉，点「CQ」→ **点下即排程、无确认框**，按时隙发射 CQ。
- [ ] 对端应答后，我方自动按序列推进：收报告 → 发 `R+报告` → 收 `RR73`/`73` → 完成。
- [ ] 或反向：对端发 CQ，点其解码行「应答」→ 自动完成整段序列。
- [ ] 中途无回复时按「放弃前重试次数」重发；达到上限即判失败并回到空闲（关闭「放弃」则一直重发）。
- [ ] 抽屉里的「停止」/「取消目标」立即静音，状态回到空闲；再次开始可正常发射。
- [ ] 发射仅在我方周期时隙窗口内，其余时间静音（对端不应在非窗口时段听到信号）。
- [ ] 收到对方**最后一条** `RR73` 后，我方回 `73` 必须仍在我方周期（对端在相反周期监听）；不得因周期重锁而发到错误时隙。
- [ ] **收到 `RR73` 真的发出 `73`（真机回归 2026-09-27）**：对方 `RR73` 到手后，下一个我方时隙必须发 `73` ——
      不得把上一时隙的旧报文（例如重复的 `R 报告`）再发一遍，更不得直接起 `CQ`。
      根因已修：① 发射比「上一时隙解码处理完」更早被排定（抢发旧报文）；② 旧报文发完时在 DONE 下清空了
      `txText`；③ 第 2 层 `SendCq` 覆盖。单测：`QsoEngineTest.keepsFinalTextWhenStaleMessageWasTransmitted`。
- [ ] **被呼叫我方必须应答，不得继续发 CQ（真机回归 2026-09-27）**：`1` 时隙里对端呼叫我，我在下一个
      `0` 时隙必须发**应答报文**，而不是再发一遍 `CQ`（更不得等到「对端再叫一次」才应答）。
      根因同上：CQ 在前导提前量处被抢发占用了该时隙 → 现在 QSO 进行中一律等解码到手再排发射。
- [ ] **发射起点 / DT（真机回归 2026-09-27）**：QSO 进行中发射改走「就地发射」，数据起点后移 ≈ 前导 + 解码延迟。
      用对端 DT 读数确认在 ±2.5 s 内且能正常解码（默认前导 250 ms → 约 +0.3 s）；若 DT 偏大影响解码，
      优先降「前导音时长 / PTT 延迟」，而不是退回抢发旧报文。
- [ ] 自动化：启用自动程序后，同一段 QSO 能**连续跑完并落库**，不需要人工干预（见 E 组）。

#### N. 发射中「关机」类操作（native use-after-free 回归）

背景：真机 tombstone 显示 `SIGSEGV in libaudioclient AudioTrack::write ← nativePlayTx ←
AudioEngine.playTx`（发射写入与关流/释放引擎并发）。已按本文档 §5.8 / §5.9 修复
（`tx_enter/tx_leave` + `out_gen` 代次 + `tx_mutex` + 销毁前 `tx_wait_idle`；Kotlin 侧
`@Volatile handle`/先清零、`stopPollingAndJoin()`、`engineGen` 丢弃迟到发射）。以下每项都要求
**进程存活**、无 `Fatal signal 11`：

- [ ] **发射中切模式**（顶栏菜单 或 设置页 6.3 模式）：等状态栏出现「发射中 <报文>」时切 FT4/FT8 →
  状态栏显示「已切换到 FTx（重建引擎，已中止本次发射）」，接收随即恢复；真机不再 SIGSEGV。
- [ ] **发射中点「停止发射」或关「发送总开关」**：状态栏出现「已停止发射…」/「发送已关闭（只接收）」，
  声音应在约 0.1 s 内停（不再响完本时隙），UI 全程不卡（总开关立即回弹成「只接收」）；进程存活，无 ANR / tombstone。
- [ ] **发射中离开 App**（划掉最近任务卡片，即 `onCleared` → `release()`；注意接收/发射中按返回键只会退到后台，不会销毁 Activity）：进程正常退出或存活，无 tombstone。
- [ ] **发射中切发射偏移「输出声卡」**：提示「输出声卡将在下次发射生效」，不打断本次发射。
- [ ] **发射本身未被改坏**：正常一次 FT8 发射仍写满整段（无 `write failed` / `tx watchdog abort` 日志），
  对端可解；设置页「测试音」仍能听到完整单音（尾部不被截断）。
- [ ] 连切模式 3–5 次（每次间隔几秒，含发射中）：接收都能恢复，`已解码时隙` 继续增长，无崩溃。
- [ ] 日志里不应出现 `nativeDestroy: playback call still alive, engine leaked to avoid use-after-free`
  （出现即说明有播放调用卡住超过 3 s，需记录机型与场景）。

补充修复（ANR 类，对应 `F_APP` 的一次真机问题「发射中关发射总开关，不停止发射，发射完成
整个程序直接崩溃」）：根因是 `AAudioStream_write` 对阻塞流会**一直等到请求的帧数全部写完**
才返回（`timeout` 只在设备卡死时兜底）。旧 `write_blocking` 一次请求「剩余全部帧」，写线程于是
**整段发射独占 `tx_mutex`**（FT8 约 16 s、FT4 约 5.5 s）；UI 线程的「停止发射」要
`stopPlayback()` 关流 → 等 `tx_mutex` → 被卡满整段发射，`txEnabled` 都来不及置 false
（表现为「关不掉、发射完整段后崩溃（ANR）」）。现改为：

① native 按 `TX_WRITE_CHUNK_FRAMES`（4096 帧，48 kHz 约 85 ms）**分块写**，`tx_mutex` 不再被整段独占；
② 新增**无锁** `nativeAbortTx`（只给 `out_gen` 加一，不关流、不加锁）供 UI 线程中止发射，
   `stopTransmit()` 不再在 UI 线程关流（关流只发生在 `stop()`/`release()`）；
③ Kotlin 侧加「发射作废代次」`txAbortGen`，丢弃已排程但尚未写声卡的那次发射。

回归取证（模拟器已实测）：设置页「测试音」（2 s / 96000 帧）日志为
`n=96000 written=96000 iters=24 elapsed=1901ms`（分块生效）；一次 FT4 整时隙发射为
`n=362304 iters=89 elapsed=7438ms`。

#### Q. 输出声卡挂起（真机 bug：「发送几次测试音后再也发不出去」）

背景：真机（华为 `LRA-AL00` / EMUI 10 / Android 10 / `HMQ4C19C03003348`）复现，logcat 实证链路：

- 「共享 + 低延迟」时 AAudio 会把输出流选为 **MMAP**（`builder_createStream  tryMMap = true for output`）。
- 该 HAL 的 MMAP 输出流**空闲数秒**后即被 AAudio 服务端挂起：
  `AAudioServiceStreamBase: writeUpMessageQueue(): Queue full. Did client stop? Suspending stream.`；
- 此后客户端每次 `AAudioStream_write` 都在 0.5 s 后返回 **0 帧**
  （`AudioStreamInternal_Client: processData(): TIMEOUT after 500000000 nanos`），
  而流句柄仍非空、状态仍 STARTED —— 于是之后**所有**发射/试音永久写 0 帧，
  用户看到的就是「发送几次测试音后再也发不出去」，只能重启 App。
- 实测「空闲时周期性写静音保活（240 帧 / 1.5 s）」**拦不住**这次挂起（挂起照旧发生，
  保活反而不断把流标坏并反复重开，进一步搅乱设备路由）。

修复：

1. 输出流改用 `AAUDIO_PERFORMANCE_MODE_NONE` → 走**传统 AudioTrack 共享路径，不再走 MMAP**。
   FT8/FT4 是时隙级时序，不需要 MMAP 的低延迟；换路后真机日志 `tryMMap = false for output`，
   `Suspending stream` 与 `processData(): TIMEOUT` 全部消失。
2. 保留「写 0 帧 / 报错 / 看门狗触发 → 标记坏流 → 下次播放前关流重开」的自愈路径
   （`out_bad` + `out_ensure_open`，试音在重开后立刻再放一次），作为其它机型的兜底；
   因此已删除原先的输出流保活线程（它既不解决问题，又制造重开风暴）。
3. 采集仍走 MMAP（真机采集正常），本次不动。
4. 按 `AAudioStream_getChannelCount()` 的**实际声道数**交错写入（单声道请求可能被 AAudio
   静默回退成立体声，否则越界读 + 波形错乱）。

验收（真机 `HMQ4C19C03003348`，2026-09-26 已实测通过）：

- [x] 设置页「播放」测试音**单击即出声**（修复前单击无声、连点两次才出声、且声音时长异常）。
- [x] 连点 5 次以上（每次间隔 3~5 s）每次都出声；中途**故意空闲 20 s 以上**再点，仍正常出声。
- [x] logcat 全程只有 **1 条** `playback started: requested=48000 actual=48000 channels=1`
  （无重开风暴），无 `output write stalled` / `tx watchdog abort`。
- [x] logcat 无 `writeUpMessageQueue(): ... Suspending stream.`、无 `processData(): TIMEOUT`。
- [x] 发射（`nativePlayTx`）与试音共用同一条输出流，行为一致；N 组（发射中关机类操作）回归不受影响。

#### R. 双方互回信号报告（真机 bug：`R-02` / `R-10` 交替死循环）

背景：两台手机互测（一端 `BG7ZJW`、另一端自造 `GB7AAA`，两端都开自动程序）复现：
解码列表里 `BG7ZJW GB7AAA R-10`（14:35:00 / 14:35:30）与 `GB7AAA BG7ZJW R-02`
（14:35:15 / 14:35:45）每 30 s 交替重复，两端都停在「发 R 报告 → 等 RR73」，
谁也不发 RR73；筛选条「回复 6」＝这 6 条全是 R 报告。

根因（第 1 层状态机缺少「收到 R → 发 RR73」这条标准 FT8 规则）：

#### R2. QSO 状态机改「报文驱动收敛阶梯」（真机 bug：`-08` / `R-10` 仍交替跑死）

背景（用户 2026-09-26 复现，一端 `BG7ZJW`、一端 `GB7AAA`）：

```
0  -1 dB -0.1s  BG7ZJW GB7AAA R-10   15:25:00
1 -11 dB +0.3s  GB7AAA BG7ZJW -08    15:24:45
0  +2 dB -0.1s  BG7ZJW GB7AAA R-10   15:24:30
1 -10 dB +0.4s  GB7AAA BG7ZJW -08    15:24:15
```

一端停在 `WAIT_RR73`（已发 `R-10`）、另一端停在 `WAIT_REPORT`（还在发纯报告 `-08`），
每 30 s 交替、永不结束。用户反馈「整个 QSO 逻辑有问题、没有自动切换自己是 CQ 方还是
应答方的能力、两台机器经常在某一个阶段跑死」。

根因（三个叠加）：

1. **状态机是「角色优先的固定脚本」**：`WAIT_RR73` 收到**纯报告**时不匹配任何转移，
   只能一直重发 R，直到重试耗尽；能否收敛完全依赖「对方听到我的 R」这一条脆弱的假设。
2. **重试按「每过一个空时隙 +1」**：两端周期相反时，每 30 s 就 +2，`maxRetries=3` → 约
   45 s 就提前放弃；放弃后第 2 层又挑同一个台、从错误阶段重启，形成
   「放弃 → 重启 → 再跑死」的抖动。
3. **自听过滤用「本批时隙最大值」整批丢弃**（`SessionViewModel`）：本批若同时含自听信号
   与对方回复，会把对方回复一起丢掉，状态机收不到回应 → 反复重发。另外第 2 层没有
   「刚完成冷却」，会把对手的残留报文当成新 QSO 重新挑起（并重复记日志）。

修复：

1. `QsoEngine` 改为**报文驱动的收敛阶梯**（类注释），任意非终态收到任意形态报文都算出
   正确下一步，角色（主叫/应答）由报文内容动态推断：
   - 收 `73` → 完成不发；收 `RR73` → 回 `73` 完成；收 `R<报告>` → 回 `RR73` 完成；
   - 收**纯报告**：若我已在 `ROGER`（回过 R 却没被对方听到）→ **直接回 `RR73` 收尾打破
     死循环**；否则转应答方、回**我自己实测的** `R<报告>`；
   - 收**网格**：仅在我尚未发报告时转主叫发报告，已发报告后的重复/滞后网格忽略。
2. 重试改为**按实际重发次数**累计（`onTransmitted` 后收到的下一个解码批次仍未推进才 +1），
   不再掐着空时隙提前放弃。
3. `SessionViewModel` 自听过滤改为**逐条**丢弃「落在我方发射时隙」的解码（空批仍交给调度器
   推进「连续无回应」计数）。
4. `AutoScheduler` 增加**完成后冷却** `QSO_REENGAGE_COOLDOWN_MS = 120 s`：同一呼号的
   定向报文（CALL/REPORT/ROGER）在冷却期内不再作为新 QSO 起点（CQ 不受限），
   手动接管的 QSO 也计入（`noteCompleted`）。

> **2026-09-30 更新（本轮 QSO 复看重做）**：上面的「报文驱动收敛阶梯」已**整体删除**，
> 改为**照 FT8CN 的报文序号模型**（`qso/FunctionOrder.kt` + 「我下一条 = 对方序号 + 1」）：
> 不再有「已回过 R 却收到纯报告 → 直接 RR73」的 4a 分支（改为按规则**重发序号 3**），
> 收尾改为引擎内的 **5 路 OR**（含「发出 RR73 后仍等对方 73」）。
> 对应单测 `alreadySentRRecoversWhenPartnerKeepsSendingReport` 已更名为
> `repeatedReportResendsRInsteadOfJumpingToRr73`；本轮口径见 §5.1.1 与 `docs/QSO.md`。
> 本文档里其余写着「收敛阶梯」的地方均为历史记录。

#### R3. 「已通联」过滤误伤定向报文（真机 bug：对方呼叫我方却始终不应答）

（R2）兜底，不再靠剔除候选来防重。设置项副标题同步改为

#### R4. 定向报文被「显示筛选 / 手动接管 / 应答状态」挡住（真机 bug：呼叫多次而不应答）

背景（用户 2026-09-26 再次复现）：现象与 R3 相同（一端反复发网格、另一端一直发 CQ），
用户要求「**要有人叫我一定应答**」。审完整条 QSO 链路后，发现除 R3 外还有三处会把
「发给我方的定向报文」直接丢掉：

1. **显示筛选误伤**：`AutoProgramSelector.collect` 用 `DecodeFilter.matches` 同时过滤
   CQ 与定向报文，而 `DecodeFilter` 就是**解码列表的标签/搜索**。用户把列表切到
   「CQ / 73 / 已通联」等页签、或输入了呼号搜索时，别人**直接呼叫我方**的报文也被一并丢掉。
2. **手动接管期间完全不处理**：`onDecoded` 开头 `if (paused || protectedStop) return None`。
   用户手动发过一次 CQ / 设过一次目标后，第 2 层被 `pause()`，此后别人呼叫我方**永不应答**。
3. **应答状态只看 CQ**：混合模式 `Phase.ANSWERING` 的 `answeringStep(cqs)` 只扫 CQ 台，

- **手动接管期间也应答**：`onDecoded` 把「定向报文 → `HandleDirected`」提到 `paused`
  判断**之前**（仅 `protectedStop` 仍然拦截）。
- **删除 120 s 完成冷却**：改为在写日志处做**同呼号 90 s 去重**（只影响入库，不影响应答），
  既满足「一定应答」，又避免上一段残留报文被重新挑起时重复记日志。
- 「报告信息优先」开关**已无作用**（定向始终优先），从设置页移除该勾选项；字段保留仅为
  兼容旧持久化数据。

#### W. 瀑布「发射频带」：红线＝下边频 + 半透明红条＝占用带宽（本轮）

背景：瀑布上原来只有一条红色竖线画在「发射频率」上，而 FT8 的**音频频率是报文的下边频**（最低那个音），
整条报文实际占用 `[f, f + 50 Hz]`（8 音 × 6.25 Hz 音距）。只画一条线会让人误以为信号只挤在那一个频点上。

改动（`engine/Ft8Engine.kt`、`ui/Waterfall.kt`、`ui/OperateScreen.kt`）：

- `Protocol` 增加 `occupiedHz`：FT8 = 50、FT4 = 83（4 音 × 20.833 Hz）；**ordinal 不变**（仍按 0/1 传 native）。
- `WaterfallView(..., occupiedHz)` 在原红线位置画**半透明红条** `0x40FF5252` 铺满 `[f, f + occupiedHz]`（全高），
  红线（`0xFFFF5252`、2px）仍画在**下边频**上 —— 拖动红线就是改发射频率，读数仍是下边频。
- 纯函数 `txBandPx(selectedFreqHz, occupiedHz, fMinHz, spanHz, width)` 算红条两端像素 x（越界夹到 `[0, width]`），
  Canvas 只用它的返回值；`OperateScreen` 传 `occupiedHz = status.protocol.occupiedHz`。

验收（JVM 单测 `WaterfallBandTest`，5 例）：

- [x] 红条从下边频起、宽度 = `occupiedHz`；FT4 的红条比 FT8 宽（83 vs 50）。
- [x] 下边频在轴外 → 夹到 0；上边频越过右端 → 夹到宽度；下边频已到最右端 → 零宽（此时只画线）；`spanHz = 0` 不崩。
- [ ] 模拟器 / 真机：瀑布上红线右侧出现半透明红条（FT8 约 50 Hz；1280px 屏、`100–3000 Hz` 轴约 22px 宽），
      改 `TX xxxx Hz` / 切 FT4 时红条位置与宽度跟着变；红条不遮挡解码色块，单击/拖动/长按手势不受影响。

#### X. 自己发的报文在解码列表里高亮成黄底（最显眼）

背景：本机（或对端转发）**能解码到自己发出的报文**（声学耦合 / 监听口）。旧口径只在「正在发射中
且报文文本与当前发射文本完全一致」时才给黄底，**发射一结束黄底就消失**，一眼看不出哪几条是自己发出去的。

改动（`qso/DecodeHighlight.kt`）：`classify` 增加 `fromMe = CallMatch.isFrom(parsed.from, myCall)`，
与 `transmitting` 一起判为 `HighlightRole.TX`（最高优先级、整行黄底黑字）：

- **只要该行的发方呼号就是我方呼号**（含 `/P` 等复合呼号，按项目宽松口径）就高亮，
  与是否正在发射、QSO 是否推进、文本是否一致都无关；优先于「已通联 / 重复 / 新网格」等分类。
- 空呼号、**相似呼号**（如我方 `BG7ZW`、对方 `BG7ZWX`）都不判；引擎侧本来就忽略发方为自己的报文，路由不受影响。

验收（JVM 单测 `DecodeHighlightTest` 新增 6 例）：

- [x] 自己发的 CQ（`CQ DX BG7ZW OM89`）、定向报文（`BG7ZJW BG7ZW R-11`）、带 `/P` 的呼号 → `TX`

- [x] 即使该行同时命中「已通联 + 重复」也仍为 `TX`；别人发的报文 / 只差一个字母的呼号 / 未填呼号 → 不判 `TX`。

#### Y3. 多趟减谱重解（SIC）落地：默认 2 趟（本轮）

口径（用户拍板）：**实现 SIC，默认 2 趟**。原理、三个坑、实测表见 **§5.4.2**；这里只记落地口径与回归项。

  （最忙文件，模拟器）≈ 19~21 ms，相对 15 s 时隙可忽略。

#### Z. 发射途中换目标：本时隙够播完就当场重发（本轮）

口径（用户要求）：**已经开始发射时切换目标，若本时隙剩下的时间还来得及完整播完一个报文，
就直接作废正在响的那段音频、当场用新报文重新生成音频并发射**（不白等一个完整周期）。

- 判据 `TxScheduler.canRetargetInSlot(...)`（纯函数）：`前导（PTT 静默 + 前导音）+ 波形自带 0.5 s
  保护间隔 + 报文时长 + 重启余量 300 ms ≤ 本时隙剩余`，并且当前必须是我方发射时隙
  （换目标时可能刚按对方时隙重锁周期 → 那就只能在下一个我方时隙发）。
  默认前导 250 ms 时：FT8 只在时隙开头约 **1.31 s** 内、FT4 约 **1.41 s** 内生效；过窗即照旧排到
  下一个我方周期（`Ft8VoxQso` 日志打「换目标：就地重发 / 本时隙剩余时间不够播完」）。
- 触发点＝所有「换目标 / 换报文」入口：`startCqInternal`（CQ）/ `answerInternal`（应答）/
  `startAutoTarget`（菜单「呼叫 / 回复」）/ `sendOnceInternal`（逐条发送）。
- 作废走 `abortTransmit()`（非阻塞，native 最多再响一块 ≈85 ms）。**被作废的那次不再记账**：
  `transmit()` 的 `finally` 现在只在「仍是当前有效的那一次」（`abortAtPlan == txAbortGen`）时才清
  `txing` 并置 `txJustFinished` —— 否则会把没播完的旧报文当成已发出去、抢先推进 QSO 状态机
  （与「停止发射」同一口径）。
- 新报文与正在播的报文相同 → 不打断（避免无意义地重发一遍）。
- 开始 QSO（CQ / 应答 / 自动程序换目标）时会**清掉还排着的「一次性待发」报文**：否则它会抢占
  下一个时隙、把新 QSO 的第一条报文压住，状态机也不推进。
- 顺带修正：`Protocol.FT4.messageMs` 由 `4_480` 改为 `5_040`（FT4 符号周期 48 ms × 105 符号 = 5.04 s，
  与 native `FT4_SYMBOL_PERIOD = 0.048f` 一致；原 4.48 s 按 42.67 ms 算，少算 0.56 s，会让
  「就地发 / 立即发 / 换目标」的窗口偏宽）。

验收：

- [x] JVM 单测 `TxComposeTest` +5 例（只在时隙开头、含 0.5 s 保护间隔与重启余量、只在own周期、
  时隙偏移口径、FT4 窗口）；`VoxPlanTest` FT4 就地窗口按 5.04 s 更新。
- [ ] 真机：发射中（CQ / 报告 / 自定义）在时隙开头改目标 → 新报文在**本时隙**就发出去（对端可解）；
  过窗后改目标 → 只更新「下次发送」，本段照旧播完。

### 6.6 已知限制（本阶段不做）

- Hound/Fox（DXpedition）、标准序列之外的变体（`TU;` 等）、比赛报文。
- 在线地图瓦片、逐条呼号的精确 DXCC 判定（当前为呼号前缀映射实体表，详见 U7a）。（**离线栅格卫星底图已实装**，见 F 组；在线瓦片仍不做。）

- 局域网后台 / 在线日志（CloudLog / LoTW / eQSL）：**不做**（占位项已删除）；瀑布配色：**不做**（占位项已删除）。
